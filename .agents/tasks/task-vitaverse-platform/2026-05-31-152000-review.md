# Fitness challenge verification platform on Next.js App Router

A full-stack fitness platform that ties Strava OAuth, phone OTP, challenge creation, auto-verification against Strava activities, and QR-based proof-of-completion together into a single Next.js 16 application. The data layer is flat JSON files on disk, the auth is NextAuth with a credentials provider and JWT sessions, and the verification token system is a simple random UUID lookup. The platform is functional end-to-end for a single-user or demo scenario.

**Watch for:** OTP has no brute-force protection and the code is stored in plaintext alongside the user record (confirmed). Strava OAuth flow has no CSRF `state` parameter validation, so the callback is open to login-CSRF attacks (confirmed). The file-based DB has read-then-write race conditions that will corrupt data under concurrent requests (confirmed). The `/api/verify/[token]` endpoint exposes user names and challenge details to anyone with a token — no authentication required — which is intentional for QR scanning but means token entropy is the only access control (confirmed). The phone number submitted during OTP verification is never validated against what was sent in the "send" step, so a user can verify an arbitrary number (confirmed).

## High-level view

Authentication uses NextAuth's credentials provider with bcrypt-hashed passwords and JWT sessions. The implementation is sound for a demo but stores the NEXTAUTH_SECRET as a static development string in `.env.local` — fine for local dev, but the file is committed and could be mistaken for production config. There is no rate limiting on login attempts.

Phone OTP is simulated (logged to console). The send step stores an OTP and expiry on the user record but doesn't record *which phone number* the OTP was issued for. The verify step accepts any phone number alongside the correct code, marking that number as verified regardless of what was originally submitted.

Strava integration follows the standard OAuth2 authorization-code flow with token refresh. The connect endpoint constructs a proper authorization URL but omits the `state` parameter entirely (the URL params are built without one). The callback exchanges the code for tokens and persists them as plaintext on the user's JSON record.

The challenge system lets any authenticated user create challenges and attempt verification. Verification re-fetches the user's Strava activities at verify-time, filters by date range and activity type, sums distance, and compares against the target. If the target is met, a verification record with a random UUID token is persisted. QR codes are generated client-side from the token URL and displayed in the dashboard. The public `/verify/[token]` page shows green/red based on a simple DB lookup.

The data layer (`db.ts`) is synchronous file I/O with no locking. Every write reads the full file, appends, and writes back. Under concurrent requests (e.g., two users verifying the same challenge simultaneously), one write will silently overwrite the other.

<details>
<summary>Issues (7)</summary>

1. **OTP phone mismatch** — The send endpoint stores the OTP but not the phone number it was sent to. The verify endpoint accepts any phone, so a user can "verify" a number they never received a code on. Store the phone at send-time and compare at verify-time.
2. **No OTP brute-force protection** — There is no attempt counter or lockout. An attacker with a valid session can try all 1M 6-digit codes within the 5-minute window. Add a max-attempts counter that invalidates the OTP after ~5 failures.
3. **Strava OAuth missing state parameter** — The `/api/strava/connect` endpoint does not generate or pass a `state` param, and the callback does not verify one. This opens the flow to login-CSRF: an attacker can force a victim's browser to complete OAuth with the attacker's Strava account. Generate a random state, store it in a cookie or session, and validate it in the callback.
4. **File-based DB race conditions** — `readDB` then `writeDB` is not atomic. Two concurrent requests that both read, modify, and write the same collection will lose one write. Use file locks (e.g., `proper-lockfile`) or switch to SQLite for correctness under concurrency.
5. **Strava tokens stored in plaintext** — Access tokens, refresh tokens, and athlete IDs are stored as plain fields in `users.json`. If the data directory is ever exposed (misconfigured static serving, directory traversal, backup leak), all users' Strava accounts are compromised. Encrypt at rest or move to a proper database with access controls.
6. **Challenges list is unauthenticated** — `GET /api/challenges` returns all challenges without requiring a session. Any unauthenticated client can enumerate all challenges including their target distances, dates, and creator emails.
7. **Duplicated token-refresh logic** — `getValidAccessToken` is copy-pasted across `progress/route.ts`, `verify/route.ts`, and `activities/route.ts` with slight variations. Extract to a shared utility in `src/lib/strava.ts` to prevent drift.

## OTP verification bypass

The send endpoint (`/api/otp/send`) accepts `{ phone }` in the body, generates a 6-digit code, stores it on the user record as `otp` and `otpExpiry`, and logs the code to the console. Critically, it does *not* persist the phone number alongside the OTP. Later, the verify endpoint (`/api/otp/verify`) accepts `{ phone, otp }` and if the OTP matches, it writes the supplied `phone` as the user's verified phone number:

```typescript
// otp/verify/route.ts
updateUser(session.user.email, {
  phone,           // ← from the request body, not from any stored record
  phoneVerified: true,
  otp: undefined,
  otpExpiry: undefined,
});
```

An attacker who has a valid session can request an OTP for phone A, then submit the correct code with phone B, and phone B is marked as verified. The fix is to store the phone number at send-time and compare it at verify-time.

Additionally, there is no attempt limiting. `Math.random()` generates the OTP (not cryptographically secure but acceptable for a 6-digit code in this context), and the 5-minute window is long enough for automated guessing. With no lockout after failed attempts, the full keyspace of 1,000,000 codes is trivially enumerable by a script making parallel requests.

## Strava OAuth without CSRF protection

The connect endpoint constructs the Strava authorization URL:

```typescript
// strava/connect/route.ts
const params = new URLSearchParams({
  client_id: clientId || "",
  redirect_uri: redirectUri,
  response_type: "code",
  scope: "read,activity:read_all",
  approval_prompt: "auto",
});
```

No `state` parameter is included. The Strava OAuth spec supports `state` specifically for CSRF protection. Without it, the callback at `/api/strava/callback` cannot distinguish between a legitimate redirect and an attacker-initiated one. An attacker who has already authorized VitaVerse on their own Strava account can craft a link to the callback with their authorization code, send it to a victim, and the victim's VitaVerse account will be linked to the attacker's Strava. This is a login-CSRF attack — the victim now sees the attacker's activities and could verify challenges based on them.

## File I/O data layer and concurrency

Every database operation follows the same pattern:

```typescript
export function updateUser(email, updates) {
  const users = readDB<User>("users");         // read entire file
  const index = users.findIndex(...);
  users[index] = { ...users[index], ...updates };
  writeDB("users", users);                     // overwrite entire file
}
```

If two requests hit `updateUser` simultaneously (e.g., the Strava token refresh fires while the user is also verifying their phone), the second write will contain stale data that overwrites the first write's changes. This is a classic TOCTOU race. For a demo, this is acceptable with the caveat documented. For production, this needs file locking or a real database.

The same pattern applies to challenge verification: `readDB("verifications")` is followed by `push` and `writeDB`. If two users verify different challenges at the same instant, one verification record will be lost.

## Verification token as sole access control

The `/api/verify/[token]` endpoint is intentionally public — it's meant to be hit when someone scans a QR code. The endpoint returns the user's name, challenge title, distance achieved, and completion date. The only thing preventing enumeration is the entropy of the UUID token (122 bits of randomness from `crypto.randomUUID()`). This is sufficient for the stated use case, but worth noting that anyone with a verification URL can see the associated user's name.

## Challenges endpoint authorization gap

`GET /api/challenges` has no session check:

```typescript
export async function GET() {
  const challenges = readDB<Challenge>("challenges");
  return NextResponse.json(challenges);
}
```

All challenges are returned to any caller. The `POST` handler correctly requires authentication, but the listing is open. Each challenge record includes the `createdBy` field (the creator's email address), so this also leaks user emails.

## Duplicated Strava token refresh

The `getValidAccessToken` function is defined identically in both `challenges/[id]/progress/route.ts` and `challenges/[id]/verify/route.ts`. A third variation exists in `strava/activities/route.ts` as `refreshStravaToken`. If the refresh logic needs to change (e.g., to handle revoked tokens or to add error logging), it must be updated in three places. This is a maintenance hazard that will lead to drift.
